# hospital_helper 项目全景介绍（新手入门）

> 本文写给**第一次接触这个项目的程序员**。目标是：读完之后，你能在脑子里建立起
> "这个项目是干什么的、由哪些部分组成、数据从哪来、结果到哪去、每一步之间怎么衔接"
> 的完整画面。本文**不深入任何技术细节**（具体算法、字段、接口协议请看 `docs/` 下其他文档）。

---

## 1. 这个项目是干什么的？

一句话：

**你告诉它"你哪里不舒服 + 你住哪儿 + 你的偏好（预算、时间、医院级别）"，
它帮你回答"该去哪家医院、挂哪个科、哪位医生、什么时候有号"，并给出一份
可解释的推荐报告。**

它相当于一个**"就医导航 + 挂号参谋"**：

```
  用户输入                         系统输出
 ┌──────────────────┐          ┌────────────────────────────────┐
 │ "我最近高血压复发" │          │ 推荐 1~3 家医院，每家都有：        │
 │ "我在徐汇区"       │  ──→    │  · 为什么推荐（可解释的理由）      │
 │ "想控制在50块以内"  │          │  · 最近有号的时间                 │
 └──────────────────┘          │  · 挂号费                        │
                               │  · 一份完整报告 report.md         │
                               └────────────────────────────────┘
```

三个关键定位，先记住：

1. **它是"运行期原型"**：能真跑、真出结果的完整可运行链路，不是设计稿。
   当前是 PC 端（命令行 + 一个简单网页），目标是将来做成移动端。
2. **它覆盖上海**：内置了上海 450 家医院的基础数据（名称、等级、类型、
   所在区、坐标、科室清单）。
3. **它"只推荐、不代挂"**：安全底线是不真实提交挂号、不支付、不产生任何
   真实交易。"挂号"那一步是**模拟（dry-run）**，只打印"如果现在挂号会
   选什么"的步骤，让你看到完整流程长什么样。

## 2. 用生活里的类比理解整体架构

想象你开了一个**医院导诊台**，背后有一整套支撑体系。这个项目里，
每个目录/模块就对应导诊台的一个组成部分：

```
┌───────────────────────────── 导诊台（app/ 运行期代码）─────────────────────────────┐
│                                                                                    │
│  顾客说"我哪儿不舒服" ──→  接待员记录需求 ──→  参谋拍板策略 ──→  从"医院名录"筛候选    │
│         (dialogue.py)        (infer.py + LLM)      (candidates.py)   │            │
│                                                                        ▼           │
│   打印最终推荐 ◄── 给候选排序打分 ◄── 去"号源档案室"查每家最近有没有号                  │
│   (book.py 模拟挂号)  (recommend.py)   (slots.py)                            │
│                                                                        ▼           │
│   贴出报告 ◄──────────────────────────────────  医院基础资料库（hospital_intel/）    │
│   (report.md)                                    症状→科室词表（ssb_dept/）          │
│                                                    号源历史数据（slots/）            │
│                                                    排序引擎（ranking/）              │
└────────────────────────────────────────────────────────────────────────────────────┘
```

- **导诊台本身** = `app/` 目录（11 个 Python 文件，一个文件管一件事）。
- **档案室** = `hospital_intel/`（450 家医院是谁）、`ssb_dept/`（什么症状归什么科）、
  `slots/`（号源历史记录）、`ranking/`（给医院打静态分的引擎）。
- **参谋** = 一个外部的大语言模型服务（Agent Service），通过 HTTP 调用，
  本项目里**唯一的"智能"就来自它**（两次 LLM 推理都走这同一个后端）。
- **门面** = 两个入口：命令行（`app/main.py`）和网页（`app/web.py` + 一个 HTML 页面），
  两条路走的是**完全相同**的处理流水线。

## 3. 核心流程：一次请求的"9 站之旅"

这是全项目最重要的图。一次推荐请求进来后，会依次经过 9 个站点
（代码入口是 `app/main.py` 的 `run_pipeline`，每站对应一个模块）：

```
 ① 定位        把"我在徐汇区宜山路"变成经纬度坐标
 │             （问高德地图要；没网/没密钥时，用一张内置小表兜底）
 ▼
 ② 病情采集     问清：症状是什么、多大年纪、男/女、多急、预算多少、
 │             对医院级别有没有要求、是否代挂
 │             （命令行可以问最多 3 轮；网页直接填表单）
 ▼
 ③ 权重推理 ★   把 ② 的信息打包，交给大语言模型（LLM），让它输出两样东西：
 │             · 一个"权重向量"——距离、价格、等级、排队…各占多少分量
 │             · 1~5 个目标科室（比如"高血压 → 心血管内科 / 内分泌科"）
 │             LLM 的"考卷"上印着 363 个规范科室名、438 家医院目录做参考，
 │             输出必须通过程序校验，编造科室名会被打回重考
 ▼
 ④ 候选集       拿着 ③ 的科室和权重，从 450 家里筛出"够得着"的候选
 │             （先按科室找覆盖的医院 → 按距离等硬条件砍一刀 →
 │              用 ranking/ 里的打分引擎逐家打分 → 留下 K 家（约 14~60 家））
 ▼
 ⑤ 号源解析     对候选里前 12 家快速探测(probe), 前 5 家深核(deep)
 │             （五层档案室依次翻，详见 §5；查不到也绝不造假）
 ▼
 ⑥ 终排 ★     最终分 = 静态分(④) × 号源可用性(⑤); 先两级排序:
│             已核实有号 > 未核实 > 已核实无号, 同级内再比分数
│             尾终裁(第 2 次 LLM): 从深核过号源的名单里定名次/医生/理由,
│             越界或失败 → 回退上面的确定性排序
│             排出前 1~3 名推荐，并给每家写出“为什么推荐”的理由和证据
 ▼
 ⑦ 模拟挂号     对第一名做一次 dry-run 挂号演练：
 │             医院/科室/医生/时段/费用全列出来，但**绝不真提交**
 ▼
 ⑧ 回归断言     程序自动跑一组"自我体检"断言（A/B/C/D 共 4 组），
 │             检查结果是不是自洽的；任何一条失败 → 本次运行标记失败退出
 ▼
 ⑨ 落盘        两份产物写到 app/out/<本次案例>/：
               · result.json  机器可读的完整结果（每一步的输入输出都在里面）
               · report.md    人可读的 10 章节报告
```

★ = LLM 出场处。全项目恰好 **2 次** LLM 推理（2026-10-06 起, 两次都走同一个 Agent Service 后端）:
  ③ 头推理 = 权重向量+目标科室（必跑）;
  ⑥ 尾终裁 = 从“已深核号源”的名单里定最终前 3+医生+理由（只能点名,
     不许发明; 校验不过/不可用 → 回退确定性排序, 不阻断）。
除这两处外全是确定性代码。

**新手读法建议**：先把 ①→⑨ 这条主干背下来，然后按顺序读
`app/` 下的文件（locate → dialogue → infer → candidates → slots →
recommend → finalize_llm → book），你会发现**文件名几乎就是这 9 站的名字**，一一对应。

## 5. 号源数据：为什么有"5 层"？（重点概念，别跳过）

"医院最近几天有没有号"是这个项目最贵也最容易出错的信息。号源是**实时**的，
不可能每次都去 App 上抓（慢、贵、可能被限流）。所以项目设计了一个**五层
回退链**——像查档案一样，从最新鲜的往最陈的依次找，**找到第一份就停**：

```
 L1 批量观察画像      历史跑批得到的统计画像（"这家这个科通常周几放号"）
        │ 没有
 L2 整院快照          某次实际抓取留下的医院级快照片
        │ 没有/过期
 L3 实时抓取(可选)    只有显式开启 --live 才会真正去手机 App 上抓
        │ 没有
 L4 档位先验          按医院等级/类型给的通用默认值（**只是先验，不是事实**）
        │ 没有
 L5 stub 演示桩       给演示用的假数据（**明显标注是桩**）
```

**这个项目最核心的诚实原则就体现在这里**：每一条号源数据都强制标注
"它到底是哪一层来的"（`live` / 已核实缓存 / 已过期缓存 / 档位先验 / stub）。
规则是**先验和桩永远不许冒充实时事实**；如果一批推荐里连一条核实过的号源
都没有，系统会整体退回"静态排序榜"并全部标上"号源未核实"——宁可承认
"不知道"，也不装懂。

> 新手提示：如果你以后改推荐逻辑，先问自己一句"我这条结论的数据源标注
> 对了吗？"——这是本项目反复被强调的第一条不变量。

## 6. LLM 在系统里扮演什么角色？

新手最容易误解的一点：**LLM 不是大脑，只是一个"受严格约束的顾问"**。

- **它做两件事（头尾各一次, 2026-10-06 起）**：③ 看完用户病情 + 参考词表，输出"权重向量 + 目标科室"；⑥ 末尾终裁，从代码深核过号源的候选名单里定最终前 3——只能从名单里点名，不许发明医院或医生。
- **它被三重约束**：
  1. 输出的科室名必须**逐字**来自内置的规范词表（363 个），编造就打回；
  2. 输出必须通过结构校验（JSON 格式、权重和、场景枚举），连续两次不过
     就报错退出（或按文档约定走兜底），**绝不静默降级**；
  3. 召回、过滤、打分这些"算得准"的活儿全部交给确定性代码；终裁 LLM 只能在代码给出的"深核白名单"里点名排人，任何越界 → 整体回退确定性 top3。
- **它是外部服务**：本项目不包含模型，只通过 HTTP（SSE 流式）调用一个
  约定的 Agent Service（默认地址 `127.0.0.1:7988`）。跑 demo 前要保证它开着。

其余各站全是纯 Python 标准库代码，**零第三方依赖**——这是项目的刻意选择，
意味着拿到一台干净的 Python 3.8+ 环境就能跑。

## 7. 怎么把它跑起来？（最小上手路径）

```bat
:: 0. 前提：Python 3.8+；Agent Service（LLM）在跑；本目录为工作根

:: 1. 离线自检（不需要 LLM/网络，验证环境）
python app\test_llm_chain.py

:: 2. 跑一个内置演示案例（胸痛红旗 / 高血压复诊 / 儿童发育）
python -m app.main --demo red_flag

:: 3. 自由输入（命令行问答或直接给参数）
python -m app.main --loc-text "徐汇区宜山路600号" --symptom "高血压复诊, 很多年了"

:: 4. 打开网页版（浏览器访问 http://127.0.0.1:8765/，填表单 → 看实时日志 → 看推荐）
python -m app.web --port 8765
```

跑完之后去看 `app/out/` 下最新的案例目录：
- **`report.md`**：人读版报告，10 个章节，人话讲清"为什么是这几家"；
- **`result.json`**：机读版全量结果，9 站的输入输出都在里面（字段说明见 `docs/API.md`）；
- 打开 `docs/PIPELINE_FLOW.svg` 对照着看流程图，把代码跑过的每一步和图对上。

## 8. 项目的"硬规则"（改代码前必读）

README 里列了 6 条"硬不变量"，用大白话复述一遍：

1. **号源标注不得混**：每条号源必须说清来自哪一层，先验/桩永远不许冒充实时事实。
2. **没核实就明说**：整批都没核实过 → 退回静态榜并全部标"号源未核实"。
3. **LLM 挂了要大声说**：不静默降级，报错 + 给出可操作的提示。
4. **科室不许编**：LLM 说的科室必须来自规范词表，出界 → 重考 → 词表回退 → 仍无 → 报错。
5. **不真挂号**：挂号步骤永远是 dry-run；上游数据目录只读不写。
6. **回归断言每次必跑**：4 组断言任一失败 → 非零退出码，本次结果不可信。

## 9. 已知边界（避免高估它）

- 权重是 LLM 直接给的，5 套"场景基线权重"只是提示词参考，**没有真实标注
  数据调过参**——所以同一 case 两次跑，排名可能略有出入（LLM 非确定性）；
- 候选粒度是"医院"，不是"院区"，距离按主院区坐标算；
- 定位没有高德 key 时降级为 3 个内置演示坐标；
- 实时号源抓取依赖一部连着 USB 的 Android 手机（纯 ADB + UI 文本匹配，
  不用任何模型），默认不启用。
