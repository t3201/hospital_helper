# 02 · 设计上怎么把过程自动化

> 上一篇：[01_现实问题.md](01_现实问题.md) · 下一篇：[03_深入_排序是怎么算出来的.md](03_深入_排序是怎么算出来的.md)

上一篇把"要解决什么"说清楚了。这一篇讲设计：一条从"你随口说一句症状"到"3 家医院 + 最早可约日期 + 挂号步骤清单"的流水线，是怎么一层层搭起来的。

## 先看全景：九个阶段

`app/main.py` 的 `run_pipeline()` 就是总装车间，注释里写得很直白：

```
阶段 1  定位        你在哪（手动坐标 / 高德文字地理编码 / adb 手机定位）
阶段 2  对话收集     ≤3 轮自由文本，问清"谁、什么病、初诊还是复诊、预算、交通"
阶段 3  LLM 主推理   把 CaseSpec + 科室词表/医院目录喂给模型，拿到 12 维权重向量 + 目标科室
阶段 4  候选集       450 家医院 → 硬过滤 → 加权打分 → 砍到 K 家（见第 3 节）
阶段 5  号源快筛     前几家先粗查号源（probe），只取"最早日期/有无号"一行
阶段 6  号源深核     对前 6 家深查：医生名单、费档分布、示例号段（deep）
阶段 7  终级排序     静态分 × 号源效用系数 重排，未核实数据一律中性
阶段 8  LLM 终裁     把明细列表交给模型做最后一道 top3 挑选（可失败回退）
阶段 9  干跑挂号     打印 8 步操作清单，第 7/8 步留给人
```

设计上有三个大原则，后面每层都能对号入座：

1. **模型只出现在两端，中间全是确定性代码。** 推理（阶段 3）和终裁（阶段 8）是 LLM 干"判断"的活；中间打分、查号、排序全是写死的公式，可测试、可复现、可归因。
2. **每一层都有兜底，任何一层挂了，流水线降级而不是崩溃。** 比如号源一条都没核实到 → 自动退回阶段 4 的静态顺序，报告里如实标注"号源未核实"，不假装实时。
3. **未核实的数据不决定生死。** 这是整个项目最重要的一条纪律，下面单独讲。

## 1. 输入端：把"一句人话"变成结构化病例

`app/dialogue.py` 干的事很像客服：最多 3 轮自由文本问答。

- 第 1 轮问症状（"哪里不舒服、持续多久"）；
- 第 2 轮问人和事（"给谁挂、初诊还是复诊、多急"）；
- 第 3 轮问约束（"怎么交通、预算多少、想三甲还是就近"）。

问完拼成一个 `CaseSpec`：患者属性（年龄/性别/人群）、症状文本、场景线索、预算档位（`auto/zero/ten/hundred/thousand/tenk/any`）、位置。

**为什么不让用户直接填表单？** 因为代挂号的人（[01 篇痛点三](01_现实问题.md)）最擅长的是"说"，不是"填"。表单里"urgency 选哪个"这种问题他根本不知道选什么，但你说"急不急、这周能不能看上"他就接得上了。所以用对话收集。

然后是 `app/infer.py` 的"主推理"，这一步 LLM 干三件事，但**三件事都被代码关在笼子里**：

1. **给 12 个特征各一个权重**（match/等级/齐全度/距离/地铁/公交/特色科室/急诊/慢病/分级诊疗/人群适配/费用友好度），行和必须=1.0。注意：**权重是 LLM 每次问诊直接输出的绝对向量**，不是从一张固定表里查的。代码里确实有 5 套"场景基线权重"（社区首诊/慢病复诊/疑难重症/红旗急症/儿科），但它们只作为**参考**塞进 prompt 里给模型看，模型自己按这次的具体病情（急不急、贵不贵、给谁挂）调权重。
2. **选目标科室**（1~5 个，每个标 tier 1 首选 / 2 相关 / 3 弱相关）。这里有个很关键的约束：**科室名必须逐字取自一份"可约科室词表"**（`hospital_intel/dept_index.json` 里覆盖 ≥5 家医院、且是可预约门诊类的那种），代码会拿词表逐个校验，模型编造的科室名一律丢弃。为什么？因为 LLM 最容易"一本正经地造词"——给你推荐一个实际不存在、挂不了的科室。
3. **推断约束**：最多等多天（`max_wait_days`）、费用上限（`price_cap_cny`）。

还有一个"笼子"：**场景**（scenario）必须从 5 个预定义里选，不能现编——这决定了后面红旗急症要不要强制"今日必须能看上"（`red_flag` 强制 `max_wait_days=0`）、慢病要不要走分级诊疗加分等分支逻辑。

而且这一步**失败就是失败，不静默回退**：LLM 服务不可用、或两次输出都没通过结构校验，`infer.py` 直接抛错终止整条流水线，而不是偷偷换一套默认权重糊弄过去。宁可报错，不可出错——这跟"未核实数据不决定生死"是同一个安全观。

## 2. 定位：三种来源，统一坐标系

`app/locate.py` 的优先级很实用：

1. `--loc "lng,lat"` 手动给坐标——代挂号最常见的场景，子女在网页上点一下地图就完了；
2. `--loc-text "浦东新区张江"` 文字地理编码，高德 `place/text` 优先、`geocode/geo` 兜底；
3. `--loc-adb` 直接从手机上读定位（随申办设备端用）。

有个坑在注释里记着：2026-10-06 修过一个坐标转换 bug，WGS-84→GCJ-02 的两个分母漏了 `*180.0`，导致上海位置偏了 4.5 公里——**偏 4.5 公里足以把"就近"排序全打乱**。这个 bug 说明这类项目里，一个不起眼的小公式错了，下游全是错的，所以 [03 篇](03_深入_排序是怎么算出来的.md) 讲的打分每个输入都要过归一化和兜底。

## 3. 候选集：450 家怎么砍到十几家

这是整条流水线里"数据量最大"的一步，代码在 `ranking/scripts/score_hospitals.py`，被 `app/candidates.py` import 复用（同一个文件既是独立命令行工具，又是库——这是仓库里多处复用的手法）。

流程是四道闸门：

1. **目标科室**：就是第 3 阶段 LLM 已经选好的那 1~5 个科室（带 tier 1/2/3），直接拿过来用。如果 LLM 那次没选出有效科室，代码会退一步，拿 LLM 给的 `triage_term`（一个症状词）去查 `ssb_dept/triage/SYMPTOM_LEXICON.json`（1822 个症状词表），看能不能映射出科室——这是**数据查询**，不是再跑一次规则引擎；两条路都走不通，就抛错终止，不硬凑。
2. **硬过滤**：非医保 → 直接出局；超出半径（默认 25km）→ 出局；没有目标科室命中 → 出局。硬过滤不参与"权衡"，是一票否决。
3. **加权打分**：12 个特征各占一个权重，每家医院算一个 0~1 之间的 score（公式见 [03 篇](03_深入_排序是怎么算出来的.md)）。
4. **K 值剪裁**（`pick_k`）：不写死"取前 10"，而是"Top1 往下，绝对落差超阈值 或 相邻落差超 span 比例就停"，钉死在 [14, 60] 区间。为什么区间这么宽？因为轻症（社区首诊）分数拉不开，需要多查几家；疑难重症分数拉得开，查 14 家就够。**把"该查几家"也变成一个算法，而不是拍脑袋。**

砍完之后剩 K 家（十几到几十家），才进入号源查询——因为号源查询要动手机、走 adb、慢，只对值得查的医院查。

## 4. 号源查询：最贵的一步，所以分两层 + 缓存

`app/slots.py` 的注释写得很清楚，号源有 5 层来源，按优先级：

```
1) slots/profiles/slot_profile.json   观察过的快照（source=observed, TTL 90 分钟）
2) slots/out/<hid>-<slug>.json         观察快照（历史实采结果）
3) 实时抓                               slots/fetch_slots.py v2，走 adb 驱动随申办
4) slots/profiles/level_defaults.json  等级先验（没查过时给个"这等级医院大概什么情况"）
5) app/fixtures/stub_slots.json        开发用的兜底 stub
```

这里藏着整个项目最核心的一条纪律，我在 [01 篇](01_现实问题.md) 提过，这里展开——

### "未核实数据不决定生死"

看 `app/recommend.py` 里号源效用系数 `u` 的公式：

```python
# 已核实（observed 且未过期）
ok          → u = max(0.6, 1 - 0.03 * 最早可约天数) × (1 - 0.4 * 紧张度)
no_slot     → u = 0.25   # 已核实没号 → 降权但仍展示
perennial_no→ u ≤ 0.35   # 常年没号 → 硬封顶

# 未核实（unqueried / 等级先验 / 过期 / stub）
其他任何情况 → u = 1.0    # 中性！不影响排序
```

**为什么未核实要给 1.0 而不是 0？** 因为"没查到号"有两种可能：真没号，或者你压根没去查过。这两种情况在数据上是长得一样的（都缺一个字段），如果都当成"没号"处理，那 450 家里没被实时查过的 400 多家会全部沉底——这明显是错的，等于把"我们懒得查"当成了"它没号"。

所以规则是：**只有亲眼查过（observed 且 90 分钟内）的数据才允许影响排序；其他一律中性，只在结果里标注"未核实"，让人自己判断。** 这条规则让整套系统在"号源服务全挂"的极端情况下，能优雅地退回 [03 篇](03_深入_排序是怎么算出来的.md) 讲的静态排序，而不是给出一堆"没号"的错误结论。

### 两级深挖：probe → deep

为什么还要分两级？因为号源查询是流水线里**最贵**的一步——要动手机、走 adb、点科室、读页面，一家医院一个科室 5-15 分钟。

- **probe（快筛）**：只对 K 家候选里打分最高的几家，查"最早哪天有号、有没有号"两个字段，一行摘要就够。
- **deep（深核）**：对 probe 之后排前 6 名的，才深查——医生名单、费档分布（15/20/25/50/100+ 元各占多少）、示例号段。

这个"先粗后细"的划分，跟 [03 篇](03_深入_排序是怎么算出来的.md) 里 K 值剪裁的逻辑是同一个思路：**贵操作只对值得的对象做**。

### 终级排序：先分档，再比分数

号源查完之后，`app/recommend.py` 的 `finalize()` 做最终排序，这里有个容易看漏的关键设计——**它不是简单"静态分 × 号源效用"一把排**，而是**两级排序**：

```python
def _slot_tier(rr):            # 第一级：按号源状态分三档
    if rr.get('verified'):
        return 0 if rr.get('slot_status') == 'ok' else 2   # 0=已核实有号  2=已核实没号
    return 1                                                          # 1=未核实
rows.sort(key=lambda r: (_slot_tier(r), -r['final_score'], r['static_rank']))
#                                  ↑第一级        ↑第二级(档内)    ↑同分时按静态名次
```

为什么要把"已核实有号"整体排在"未核实"前面，哪怕后者的静态分更高？因为**挂号推荐的目的是找到"能挂上的号"**。一家评分 0.90 但没查到号的医院，对"这周想看好"的用户来说，不如一家评分 0.70 但确认明天就有号的医院有用。所以：

- **第一级**：已核实有号（第 0 档）> 未核实（第 1 档）> 已核实没号（第 2 档）；
- **第二级**：同档内再比 `final_score = 静态分 × 号源效用`。

这一级设计有个漂亮的自洽结果：**如果这一轮一家医院都没核实到号源（比如号源服务全挂），那所有医院都落在"未核实"这一档，档内就按静态分排——于是终级排序恰好退化成第 4 阶段的静态顺序**。这不是额外写的兜底分支，而是两级排序规则的自然推论。这就是 [01 篇](01_现实问题.md) 说的"可追溯"、和这里反复出现的"未核实不决定生死"，在同一段代码里的交汇。

## 5. 终裁：模型做"最后一公里"的判断

阶段 8 的 LLM 终裁（`app/finalize_llm.py`）很有意思——它不是让模型自由发挥，而是给它一份**已经核实过的明细列表**，让它做最后 3 家挑选。系统提示词里写得很死：

```
你只能从「明细列表」中挑选最终前 3 家医院并排序。
不得选择明细列表之外的医院，不得编造 hospital_id 或医生名;
doctor 字段 = 该医院「可约医生」里出现过的名字, 或 null;
取舍得优先级: ①最早可约日期 ②费档 ③科室 tier ④医生职称/专长匹配 ⑤医院等级与距离
```

也就是说，**模型的输出被限制在"从已核实数据里挑 + 排序 + 写 30 字理由"** 这个小箱子里。它不能创造医院、不能创造医生名、不能脱离"日期/费档/tier"这条既定优先级。这样即使模型偶尔抽风，最坏情况也只是"top3 顺序不太对"，不会"给你推荐一家不存在的医院"。

而且这一层挂了不影响交付：`finalize_llm.run_final` 返回 None 时，`app/main.py` 回退到阶段 7 的确定性 top3，用户照样拿到结果。这就是"两端模型 + 中间确定性 + 每层有兜底"的第三条腿。

## 6. 输出端：干跑挂号，机器只到第 6 步

`app/book.py` 只有 49 行，但它是整套系统的"安全阀"，我把它的逻辑完整搬给你看：

```
第 1 步  打开随申办 mobi.w3studio.apps.android.shsmy.phone
第 2 步  首页 → 预约挂号 → 全部医院(444)
第 3 步  选医院: <name>
第 4 步  选科室 tab: <dept_tab>
第 5 步  选日期: <earliest_date>
第 6 步  选医生/时段 → 「去预约」
第 7 步  就诊人 + 短信验证码      ← 需要你本人操作
第 8 步  最终确认 + 支付          ← 需要你本人操作
```

前 6 步是"读 + 点导航类按钮"，没有风险；第 7 步开始涉及身份验证，第 8 步涉及支付。`book.run(execute=True)` 这个入口本身是存在的，但它**永远返回一条拒绝信息**，把 `--execute` 参数直接挡掉。`app/patients.py` 的注释也是同一个纪律：只点"预约挂号/就诊人/返回/同意"，**绝不点**"新增就诊人/绑定就诊卡/去预约/提交/支付"。

这条红线在 `hospital_intel/manifests/` 的 450 家医院档案里也有体现——每家都标了 `capabilities.book=false`。也就是说，从数据层就声明了"这个系统没有真正的挂号能力"，机器只做它该做的事：**把决定做好，把执行留给人**。

## 7. 手机 App 端：同一套流水线换个壳

`mobile/controller-app/` 是 Android 应用，用 Chaquopy 把 Python 3.13 塞进 APK 里，`app/` 下那套九个阶段的代码**原封不动复用**。区别只在设备桥：

- PC 上走 `adb` + `uiautomator`（PC 连手机远程驱动）；
- 手机上走 `SsAccessibilityService`（自建的无障碍服务，App 自己点自己）。

`SsAccessibilityService.java` 是核心，它替代了 PC 上 adb 的角色，让 App 能在真机上直接操作随申办。`TaskEngine.java` 跑九个阶段，`AgentClient.java` 走 SSE 连 LLM 服务，`ResultRenderer.java` 渲染结果。

所以整个项目可以这么理解：**一份 Python 核心（`app/` + `ranking/` + `slots/` + `hospital_intel/`），两种壳（PC 命令行 / Android App），一条红线（绝不代点支付）**。

## 小结

这一篇把"设计"讲完了，串起来看就是：

```
一句人话 ──对话──> CaseSpec ──LLM(直出权重向量+科室+约束)──> 12维权重
    ──triage+硬过滤+打分+K剪裁──> 候选 K 家
    ──probe快筛 + deep深核──> 已核实号源
    ──两级排序(先号源状态分档, 档内静态分×号源效用)──> 重排
    ──LLM终裁(top3+理由)──> 结果
    ──干跑挂号清单(到第6步)──> 交付给人
```

三根支柱：**两端模型+中间确定性**、**每层有兜底**、**未核实不决定生死**。下一篇钻进最核心的一步——打分——看一个 0~1 的分数到底是怎么一步步凑出来的。
