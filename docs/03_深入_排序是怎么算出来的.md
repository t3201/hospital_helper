# 03 · 深入：一个 0~1 的分数是怎么算出来的

> 上一篇：[02_怎么把过程自动化.md](02_怎么把过程自动化.md) · 回入口：[index.md](index.md)

前两篇讲"解决什么问题"和"整体怎么搭"。这篇钻进最核心的一步——**候选集打分**——用大白话把公式里每一个数字的来源讲清楚。看完这篇，你对这个项目该有相当具体的印象了：它不是黑盒，每个分数都能倒推。

代码在 `ranking/scripts/score_hospitals.py`，被 `app/candidates.py` import 复用。下面按打分流程一步步走。

## 第 0 步：先把"等级"、"距离"、"科室数量"这些天差地别的原始值，压到 0~1 之间

这是整个打分前最容易被忽略、但最要命的一步。原始数据长这样：

- 医院等级：三级甲等 / 二级 / 一级乙等……**没有数字**；
- 科室数量（二级科室数）：从 3 个到 200 多个不等，**是个长尾分布**；
- 距离：0.5 公里到 80 公里；
- 公交站点数：0 到 20 个。

这些量纲完全不同，不能直接相加。所以项目里给每个特征配了一个"归一化"函数，把各自压到 0~1。挑几个看：

**等级 → 分数**（`LEVEL_SCORE_MAP`）：

```
三级甲等  → 1.00
三级乙等  → 0.72
二级甲等  → 0.50
一级乙等  → 0.18
未定级    → 0.28   # 注意：不是 0！
```

为什么"未定级"给 0.28 而不是 0？因为"没查到等级"和"确实是低等级"是两回事——给 0 会冤枉那些数据缺失但其实不错的医院。这个 0.28 是一个"我大概不知道，但倾向偏低"的估计值，不是惩罚分。

**科室齐全度 → 分数**（`breadth`）：

```python
breadth = min(1.0, log1p(科室二级数) / log1p(142))
#                                              ^^^^^
#                                        142 = 全量医院的第 90 百分位
```

为什么用 `log1p`？因为科室数分布是长尾的——有少数医院 200 多个科室，绝大多数只有几十个。直接线性映射，那几家"巨无霸"会压扁其他所有医院。取对数之后，从 10 个科室到 50 个科室的提升幅度，和从 100 到 200 的提升幅度，在分数上不会差太多——更符合直觉（多 30 个科室和少 30 个科室，"好不好"的差距确实不该那么悬殊）。

为什么分母用 142（p90）而不是最大值？如果用最大值，那绝大多数医院的 breadth 分数都会挤在 0.5 以下，区分度不够；用第 90 百分位做分母，意味着"排进前 10% 的医院"才会拿到接近 1.0 的分数，中位数医院大约在 0.6 左右——区分度更合理。

**距离 → 分数**：

```python
distance_score = max(0.0, 1.0 - 距离公里 / 25)
#                                            ^^^
#                                        25km = 上海市域距离衰减上限
```

0.5 公里 → 0.98；10 公里 → 0.60；25 公里 → 0.0。超过 25 公里的医院直接 0 分（配合硬过滤的半径限制，基本也进不了候选集）。

**公交站点 → 分数**：

```python
bus_score = min(1.0, log1p(站点数) / log1p(5))   # 5 = 全量第 90 百分位
```

0 个站点 → 0；1 个 → 0.39；3 个 → 0.67；5 个 → 1.0；超过 5 个的都封顶在 1。（分母用 p90=5 做"满分线"，意味着 300m 内有 5 个及以上公交站点就算满分，更少的按比例递减。）

## 第 1 步：数据缺失/低置信度时，怎么办？

这是这个项目设计里非常细腻的一点，`score_hospital` 里反复出现两种处理：

**值缺失（None）→ 直接给 0.5（中性）**

```python
NEUTRAL = 0.5

if rec['dept_breadth'] is None:
    add('breadth', NEUTRAL, '缺失→中性0.5')
elif rec['lng'] and rec['lat']:
    add('distance', ...)
else:
    add('distance', NEUTRAL, '无坐标→中性0.5')
```

为什么缺失给 0.5 而不是 0？道理跟"未定级"一样：**"没查到"和"真的差"是两回事**。如果缺失=0，那所有数据不全的医院都会被系统性地往下压，而数据不全往往不是医院本身的错（可能是采集时没爬到）。给 0.5 相当于说"我不知道它好不好，先不算它好也不算它差，别影响排序"。

**低置信度（provenance.confidence='low'）→ 向 0.5 混合 40%**

```python
LOW_CONF_BLEND = 0.40

def blend_low(v, low):
    if low:
        return (1 - 0.40) * v + 0.40 * 0.5
    return v
```

举个例子：某医院等级查出来是"二级甲等"（0.50），但数据来源标注 confidence=low（比如是猜的、不是官网直接拿的）。那么最终参与打分的值变成：

```
0.6 × 0.50 + 0.4 × 0.5 = 0.30 + 0.20 = 0.50
```

碰巧没变。换一个例子：等级"三级甲等"（1.00）但 confidence=low：

```
0.6 × 1.00 + 0.4 × 0.5 = 0.60 + 0.20 = 0.80
```

从 1.0 被拉低到 0.80——**不是否定它，而是说"这个数据我有点没把握，所以往中间收一收"**。这个"向中性收缩"的手法，在 [02 篇](02_怎么把过程自动化.md) 讲的"未核实数据不决定生死"大原则下，其实是同一个思想在打分层的具体体现：不确定信息不该过度影响结论。

## 第 2 步：12 个特征，每个特征贡献多少分？

`score_hospital` 函数里，每个特征都走同一个模式：

```python
def add(name, v, note=''):
    w = weights.get(name, 0.0)     # 权重（LLM 这次问诊直接输出的向量；见下）
    if w <= 0:
        return                    # 权重 0 = 这次问诊不看这个特征
    v = max(0.0, min(1.0, v))      # 夹到 [0,1]
    contribs.append({
        'feature': name,
        'weight': w,
        'value': round(v, 4),
        'contribution': round(w * v, 4),   # ← 这个特征给总分加了 w*v
        'note': note,                       # 人类可读解释
    })
```

`contribution = weight × value`，最后总分就是所有 contribution 之和。这就是为什么**权重表的行和必须等于 1.0**——这样每家医院的分数都落在 [0, 1] 之间，而且"分数高低"可以直接读出来：1.0 是"所有特征都完美"，0 是"所有特征都最差"。

下面把进入这一步静态打分的特征一个个说。**具体每个特征占多少权重，是第 3 阶段 LLM 每次问诊直接算出来的绝对权重向量**（行和=1.0；LLM 输出的是 12 维，其中 `price`/费用友好度 那一路不在这一步打分里，而是作用在终排的号源效用上，[02 篇](02_怎么把过程自动化.md) 讲过）。这里借"慢病复诊"这套专家先验基线权重当**代表示例**来讲每个特征怎么取值——真实运行时权重会按当次病情浮动，但"特征取值 0~1 + 加权求和"的机制完全一样。

### 特征 1：match（科室命中质量）— 权重 0.26

这是最重要的特征。逻辑是：对每个目标科室，检查这家医院有没有这个科室；有，就按"命中质量"给分，取所有命中科室里的最大值；一个都没命中 → 0。

命中质量 = `PRIORITY_W[priority] × CONF_W[confidence]`：

```
PRIORITY_W = {1: 1.00, 2: 0.70, 3: 0.45}     # 科室层级：首选/相关/弱相关
CONF_W     = {'high': 1.00, 'mid': 0.85, 'low': 0.65}   # 置信度
```

这里要说明一个容易误解的地方：目标科室从哪来、`priority/confidence` 从哪来，取决于走的是哪条路（见 [02 篇](02_怎么把过程自动化.md)）：

- **LLM 主路径**（绝大多数情况）：LLM 逐字从科室词表里直选出的科室，在 `app/candidates.py` 的 `_targets_from_canonicals` 里被**统一构造为 `priority=1, confidence='high'`**——也就是说 LLM 选定即视为"首选 + 高置信"，命中质量恒为 1.0。此时"这家医院有没有这个科室"本身就是 0/1 的硬判断（能进候选集就已经命中了），match 分数主要靠**权重**拉开差距。tier 1/2/3 的区分更多体现在 prompt 引导 LLM 选哪些科室、以及终裁阶段挑 top3 时的取舍上。
- **症状词表兜底路径**（LLM 没选出有效科室时才走）：从 1822 词表里映射出的科室，才带真正的 `priority`（1/2/3）和 `confidence`（high/mid/low）——这时候"首选+高置信 → 1.0；弱相关+低置信 → 0.45×0.65 ≈ 0.29"的梯度才会真正起作用。

两条路都保证了一件事：**match 分数只反映"这家医院到底有没有对症的科室"，不会被"数据里科室条目的来源可信度"污染**。

注意 `ALLOWED_HIT_KINDS = {'clinic', 'specialty_clinic', 'screening'}` 这个过滤——科室数据里有些条目是"预约条目"、"疫苗接种"、"影像检查"之类的辅助条目（kind=ancillary/other/site），**这些不算"有科室"**，不能用来证明"这家医院能看这个病"。这是个很实际的坑：数据里一个"XX医院 疫苗接种"条目，不能用来当"这家医院有儿科"的证据。

### 特征 2：level（医院等级）— 权重 0.08

就是上面讲的 `LEVEL_SCORE_MAP` 查表 + `blend_low` 低置信度收缩。慢病复诊场景里这个权重很低（0.08），因为分级诊疗的原则是"小病下沉"，三级甲等不是加分项反而是减分项（排队太久、太贵）。

### 特征 3：breadth（科室齐全度）— 权重 0.10

就是上面讲的 `log1p(l2)/log1p(142)`，缺失给 0.5。

### 特征 4：distance（距离）— 权重 0.26

就是 `max(0, 1 - km/25)`，无坐标给 0.5。慢病复诊场景里距离权重比社区首诊（0.28）略低，但仍是第二重要——复诊的人最不想每次都跑很远。

### 特征 5：metro（地铁可达性）— 权重 0.07

优先用"步行到最近地铁站的分钟数"，没有就用"直线距离"：

```python
metro = 1.0 - min(1.0, 步行分钟 / 30)    # 30 分钟 = 满分上限
# 或
metro = 1.0 - min(1.0, 直线距离米 / 2500)
```

5 分钟 → 0.83；15 分钟 → 0.50；30 分钟以上 → 0。低置信度同样走 `blend_low`。

### 特征 6：bus（公交站点）— 权重 0.05

就是 `log1p(站点数)/log1p(5)`。

### 特征 7：key_specialty（特色科室）— 权重 0.03

这个特征有点特殊：**它不缺失就给中性，而是缺失就给 0**。

```python
if ks:  # 有特色科室记录
    hit = any(...)   # 检查目标科室里有没有命中特色科室
    add('key_specialty', 1.0 if hit else 0.0, ...)
else:
    add('key_specialty', 0.0, '空（覆盖4.4%）')   # 不是 0.5！
```

为什么这里不缺失给 0.5？因为"特色科室"这个字段本身覆盖率只有 4.4%（450 家里只有 20 家有记录），**不是数据缺失，而是绝大多数医院确实没有特色科室**。给 0.5 等于在替 430 家没有特色科室的医院"虚报"一个不存在的加分项。所以这里缺失=0 是对的。

**这是一个很好的例子，说明"缺失给 0.5"不是无脑套公式，而是要看这个字段的缺失到底意味着什么。**

### 特征 8：emergency（急诊能力）— 权重 0.10（仅 red_flag 场景有）

```python
emergency = 1.0 if 该医院有任一急诊类科室 else 0.0
```

红旗急症场景下，有急诊的医院直接加 0.10 分，这是个"一票加权"——不是"锦上添花"，而是"救命"。

### 特征 9：chronic（专病随诊）— 权重 0.05（仅 chronic 场景有）

```python
chronic = 1.0 if 命中科室里有"专病"visit_type else 0.0
```

慢病复诊场景下，如果目标科室里有"高血压专病门诊"、"糖尿病专病门诊"这类带"专病"标签的 visit_type，就加分——说明这家医院专门做慢病管理，复诊体验更好。

### 特征 10：chronic_fit（分级诊疗承接）— 权重 0.10（仅 chronic 场景有）

```python
fit = 医院等级分数 ≤ 0.50（即二级及以下） AND 有 p1 首选科室命中
chronic_fit = 1.0 if fit else 0.0
```

这是最"政策性"的一个特征：**低等级医院（社区/二级）+ 有合适的专病科室 → 加分**。逻辑是分级诊疗——高血压复诊这种稳定慢病，本来就该在社区/二级医院看，不该挤三甲。这个特征让"社区医院有高血压专病门诊"这种情况，比"三甲医院有心血管内科"在复诊场景里更有优势，即使三甲等级更高。

### 特征 11：age_fit（人群适配）— 权重 0（peds 场景才有，其他场景恒为 1.0）

peds（儿科）场景下三档：

```
儿童专属机构（名字含"儿童医院/儿童医学中心/儿科医院/复旦儿科"） → 1.0
有儿科类科室（非专属）                                              → 0.75
无明确儿科科室                                                    → 0.5（中性，不惩罚）
```

注意这里用的是 0.5（中性）而不是 0，跟"未核实"的处理思路一致：**没有儿科科室不等于"不能看儿科"，只是没把握，先不加分也不减分**。

## 第 3 步：总分 = 所有 contribution 之和

以 `chronic_followup` 场景为例，权重表是：

```python
{
    'match': .26, 'level': .08, 'breadth': .10, 'distance': .26,
    'metro': .07, 'bus': .05, 'key_specialty': .03, 'chronic': .05, 'chronic_fit': .10,
}
```

行和 = 0.26+0.08+0.10+0.26+0.07+0.05+0.03+0.05+0.10 = **1.00** ✓

假设某医院：match=0.70（首选+mid）、level=0.50、breadth=0.60、distance=0.60、metro=0.50、bus=0.80、key_specialty=0（无）、chronic=1.0（有专病）、chronic_fit=1.0（二级+有p1）：

```
contribution:
  match         = 0.26 × 0.70 = 0.182
  level         = 0.08 × 0.50 = 0.040
  breadth       = 0.10 × 0.60 = 0.060
  distance      = 0.26 × 0.60 = 0.156
  metro         = 0.07 × 0.50 = 0.035
  bus           = 0.05 × 0.80 = 0.040
  key_specialty = 0.03 × 0   = 0.000
  chronic       = 0.05 × 1.0 = 0.050
  chronic_fit   = 0.10 × 1.0 = 0.100
─────────────────────────────────
总分           = 0.663
```

这个数字落在 [0,1] 之间，可以直接读出来：**这家医院在慢病复诊场景下，综合表现大约是"满分"的 66%**。而且因为每个 contribution 都记录了 feature/weight/value/note，`explain()` 函数能倒推出"这家医院为什么是 0.663：距离 10km（0.156 分）、命中首选科室（0.182 分）、二级医院承接慢病（0.10 分）……扣分主要是 metro 步行 15 分钟（0.035 分）"。

**这就是 [01 篇](01_现实问题.md) 讲的"可追溯"——不是口号，是代码里每个 add() 调用都自动记录下来的。**

## 第 4 步：硬过滤 —— 一票否决，不参与权衡

打分之前，`hard_filters` 先过一遍：

```python
def hard_filters(hid, rec, radius_km, require_insurance, target_hit):
    if rec['blocked']:                        # verify=wrong（数据核实为错误）
        return False, 'BLOCKED(verify=wrong)'
    if require_insurance and mi == 'no':      # 非医保
        return False, '非医保'
    if km > radius_km:                         # 超出半径
        return False, '超出半径%.0fkm(%.1f)'
    if not target_hit['hit']:                  # 无目标科室命中
        return False, '无目标科室命中'
    return True, ''
```

注意顺序：BLOCKED（数据本身错了）→ 非医保 → 超出半径 → 无科室命中。BLOCKED 排在最前面，因为那是"这家医院的数据本身有问题"，比其他任何条件都严重。

**硬过滤和打分是两套逻辑**：硬过滤是"0 或 1，没有中间状态"，不参与任何权衡；打分是"在通过硬过滤的医院里，排个先后"。这样设计的好处是：硬过滤的条件（比如"非医保"）不会因为"这家医院其他方面特别强"就被绕过——**硬约束就是硬约束**。

## 第 5 步：K 值剪裁 —— "该查几家"也是一个算法

打完分之后，不是简单"取前 10"，而是 `pick_k` 函数动态决定：

```python
K_MIN, K_MAX = 14, 60
K_ABS_DROP = 0.22          # 相对 Top1 的绝对落差地板
K_GAP_FRAC = 0.15          # 相邻落差阈值 = max(0.05, 0.15 × span)

def pick_k(scores_desc):
    # 条件 A：从 Top1 往下，分数 ≥ Top1 - 0.22 的都算"够格"
    floor = scores_desc[0] - 0.22
    i_floor = 第一个分数 < floor 的位置

    # 条件 B：相邻两家医院的分数落差超过 max(0.05, 0.15×span) → 断崖，停
    gap_thr = max(0.05, 0.15 * (scores_desc[0] - scores_desc[-1]))
    i_gap = 第一个相邻落差 > gap_thr 的位置

    k = min(i_floor + 1, i_gap)
    k = max(14, min(60, k, n))    # 钉死在 [14, 60]
```

为什么这么设计？因为不同场景下分数分布差异很大：

- **轻症（社区首诊）**：450 家医院里可能有 200 家分数都在 0.4~0.6 之间，区分度很低，需要查 20+ 家才能找到"真正合适的"；
- **疑难重症**：分数拉得很开，Top3 和 Top10 之间可能就 0.05 的差距，查 14 家就足够了。

**K 值不是拍脑袋定的，而是从分数分布本身推出来的**——这也是"把'该查几家'变成一个算法"的具体实现。

## 小结：三层保护让"打分"这件事变得可信

| 层次 | 做法 | 为什么 |
|---|---|---|
| 归一化 | 每个特征各自压到 0~1，用对数/分位数处理长尾 | 不同量纲可比，长尾不压扁正常值 |
| 缺失/低置信处理 | 缺失→0.5 中性；低置信→向 0.5 收缩 40% | "没查到"≠"真的差"，不确定信息不过度影响结论 |
| 贡献可追溯 | 每个 add() 都记录 feature/weight/value/note | 每个分数都能倒推"为什么"，`report.md` 直接可读 |

这三层合起来，就是 [01 篇](01_现实问题.md) 里说的"可追溯"、[02 篇](02_怎么把过程自动化.md) 里说的"未核实数据不决定生死"、以及"两端模型+中间确定性"——三条设计原则，最终都落到了 `score_hospital` 这一个 400 行函数里。
