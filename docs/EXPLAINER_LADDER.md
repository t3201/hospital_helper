# 从"挂号难"到一套代码：一层一层读懂本系统

> 读者预设：完全不懂技术。本文从生活场景出发，一层一层往上爬，
> 每上一层就离代码近一点，直到最后链接到具体源文件与其它文档。
> 每一节末尾都有"🔗 去哪看"（源码文件 / 其它文档），方便想深究时直接跳。
>
> 一句话总览：**它不给你"诊断"，它给你"该去哪家医院、挂哪个科、大概几天后能约到、花多少、为什么"**，
> 然后**只告诉你怎么挂，绝不替你挂**。

## 第 0 层 · 它到底在解决什么现实问题？

先不谈代码。想象这几个真实场景（都是"挂号难"的典型）：

- **场景一（急，但不知道急不急）**：孩子半夜发烧 39.5℃，家长又慌又困，打开手机不知道该去社区、去儿科急诊，还是去儿童医院，更不知道现在哪家还有急诊号。
- **场景二（慢，但不知道找谁）**：一位老父亲长期高血压、血糖偏高，想看"能长期管慢病"的医院，最好离家别太远、别太贵，但 450 家医院他一个都记不全。
- **场景三（口语 vs 专业）**：你只知道自己"嗓子痛、鼻塞"，但你**说不出**该挂"耳鼻喉科"。系统里 438 家医院、几百个科室名，你没法自己对着清单找。
- **场景四（代挂，信息不全）**：女儿帮 80 岁老人挂骨伤的号，老人说不清细节，女儿也不知道哪家"骨科"强、哪家其实有"创伤骨科"这种更细分的科。

**这些场景背后是同一个真实痛点：**

> 看病这件事，"信息"和"决策"是割裂的——你有一肚子模糊的症状和一堆约束（近、便宜、快、老人小孩、哪个科），
> 但没有任何一个入口把这些**合起来**，直接告诉你"去这 3 家、挂这个科、最快几天能约到、大概多少钱、为什么是它"。
> 现有 App（如随申办）给你的是**海量选项**，把"从海量里挑对的"这件最难的活，留给了最焦虑、最不懂的那个人。

**本系统做的事，就是把"挑对的"这件活自动化**，而且**把"我怎么挑的"全程写给你看**。

## 第 1 层 · 把"看病"拆成 7 个具体小问题

任何复杂系统，本质都是把一个大问题拆成一串小问题逐个解决。
把上面那些场景揉一揉，你会发现"挂号推荐"其实要回答 7 个递进的小问题：

| # | 小问题（人话） | 不解决会怎样 |
|---|---|---|
| **A** | **我在哪？离哪些医院近？** | 推荐一堆 40 公里外的医院，形同虚设 |
| **B** | **"我说的症状"机器听得懂吗？** | "嗓子痛"被当成"喉咙发炎"，推错科 |
| **C** | **一个症状可能对应好几个科，哪个最对？** | 嗓子痛推"呼吸科"还是"耳鼻喉科"？选错白跑 |
| **D** | **450 家里，谁同时满足"近+对+强+便宜"？** | 无从下手，只能凭名气瞎猜 |
| **E** | **挑出来的这几家，到底哪家真有号？** | 推荐了一堆没号的医院 → 最大的坑 |
| **F** | **有号了，怎么挂？谁来挂？** | 要么用户不会操作，要么系统越权真挂了 |
| **G** | **这套推荐凭什么可信？我怎么信？** | 推荐错科/错医院，后果严重，必须可追责 |

**注意这个顺序**：A→B→C 是"听懂需求"，D 是"圈候选"，E 是"验有没有号"，F 是"怎么落地"，G 是"信任与审计"。
下面每一层，就是把其中一个问题往上爬一级。

## 第 2 层 · 每个小问题对应一个"设计选择"（仍是半人话）

下面把第 1 层的 7 个问题，逐个配上"我们打算怎么解"。这一层**不谈代码**，只谈思路。

### A. 我在哪 → **定位 + 兜底**
把"我在静安"或 GPS 坐标，解析成标准经纬度（上海用高德坐标 GCJ-02）。
**关键：万一没网、没高德 Key，也不能崩**——所以备了一份"内置城市兜底表"（静安/浦东/…→ 固定坐标）。
并且**同样的位置只查一次**（30 天缓存），下次直接命中，不重复调外部接口。

### B. 听得懂症状吗 → **交给"会说话的大脑"理解，别用死规则**
最直觉的做法是维护一张"关键词表"（嗓子痛→耳鼻喉）。但人的说法无穷无尽，死规则必然漏。
所以这里**把症状原文直接交给大语言模型（LLM）去理解**，让它说出"这是什么情况、大概哪个科、急不急、能等几天、预算多少"。
> 但 LLM 会"编"，所以它说的话必须被**逐项核验**（下一层细讲）。

### C. 哪个科最对 → **让模型排出"首选 / 相关 / 弱相关"三档**
不是只选一个科，而是让 LLM 给出 1~5 个科并分档：
- **首选（tier 1）**：症状直接指向它（如"喉咙痛→耳鼻喉科"）
- **相关（tier 2）**：也能看/常见首诊
- **弱相关（tier 3）**：邻近或保守后备

这样"推错一档"的代价就被摊薄了，而不是押死在一个科上。

### D. 谁综合最优 → **给每家医院打一个"综合分"**
把"科室命中、医院等级、科室齐全、距离、地铁、公交、特色科、急诊、慢病承接…"
这些维度各给一个权重（权重来自 B 里 LLM 的判断），加权算出一个 0~1 的综合分，从高到低排。
**这一步是纯计算、可复现、可审计**——同样的输入必然给出同样的分数。

### E. 哪家真有号 → **这是系统最核心、也最诚实的一层**
前面 D 只排出了"理论上合适的医院"，但**合适 ≠ 现在能约到**。
所以系统引入一个关键概念——**"核实"（verified）**：
- **已核实的号**（真实抓到过、且在有效期内）才算数；
- **没核实的**（没查到、只有经验估计、演示假数据）**一律标注"未核实"，绝不伪装成实时事实**。

**设计原则（这是全系统的灵魂）：宁可明说"我不知道有没有号"，也绝不编一个"有号"。**

### F. 怎么挂 / 谁来挂 → **只给步骤，绝不真挂**
系统**只输出一份"如果你要挂，该怎么操作"的步骤清单**（打开哪个 App、点哪个科、选哪天、哪位医生），
**实名、验证码、支付这些真正产生交易、涉及隐私的动作，明确划给用户自己完成**。
"真帮你挂号"这条能力，在原型里是**硬边界**——不是可选开关，而是被拒绝的。

### G. 凭什么可信 → **每条结论都留痕 + 每次运行都做自检**
- **留痕**：每个"有号/无号/多少钱/来自哪"都带**出处**（哪层数据、抓的哪个文件、抓于何时）；
- **自检**：每次跑完都自动执行一组"回归断言"，专门抓"最好的医院被莫名丢掉""查过号的医院无声蒸发"这类系统性错误，**任一失败就整次标记为不可信**。

## 第 3 层 · 把 7 个问题串成一条"9 步流水线"

把第 2 层的思路按顺序接起来，就是系统实际执行的一条流水线（CLI 和网页版**跑的是同一条**）：

```
① 定位        —— 解决问题 A（我在哪）
② 对话采集    —— 症状 + 就诊人信息 + 偏好（1 轮自由描述 + 可选 ≤2 轮补充）
③ 权重推理    —— 解决问题 B/C（听懂症状 + 排出科）★ 唯一用到 LLM 的一步
④ 候选集      —— 解决问题 D（打分排序，圈出 14~60 家）
⑤ 号源解析    —— 解决问题 E（哪家真有号，五级数据源）
⑥ 终排推荐    —— 把"合适"和"有号"合起来，给出 1~3 家推荐 + Top-N 列表
⑦ 模拟挂号    —— 解决问题 F（只给步骤，不真挂）
⑧ 回归断言    —— 解决问题 G（自检，抓系统性错误）
⑨ 落盘        —— 存下完整结果（JSON + 人类可读报告）
```

**这条流水线最重要的一个"铁律"：第 ③ 步是唯一会"发挥"的（LLM 非确定），
其余 ①②④⑤⑥⑦⑧⑨ 全是确定性代码——同样的输入必然得到同样的输出。**

换句话说：**系统把"不可控"压缩到最小的一块，其余全部做到可复现、可审计。**

### 4.1 第③步"权重推理"：LLM 到底被允许做什么、被限制什么

**它被要求直接吐出一个 JSON**，包含：`scenario`（5 选 1 的场景）、
`weights`（12 个维度的权重）、`dept_canonicals`（1~5 个科室+分层）、
`triage_term`、`max_wait_days`、`price_cap_cny`、`reasoning`。

**三重约束防止它"编"：**
1. **科室名逐字校验**：LLM 给的科室名，必须能在"可约科室词表"里**逐字找到**，
   且类别必须"可预约"。找不到的直接判无效。（这是防"编造科室"的硬闸门）
2. **结构校验**：JSON 格式、scenario 枚举、权重全为正、归一化到和=1.0 等，全部用代码检查。
3. **失败即终止，不静默降级**：两次都通不过校验 → **直接报错退出**，
   不会偷偷换成一套规则硬撑（因为那样会把"没听懂"伪装成"听懂了"）。

**一个关键的批判点（值得记住）：** 上面第 1、2、3 条都是**硬约束**，
但**"科室分层必须拉开"（首选和弱相关不能都给 1）只是 prompt 里的软要求**，
代码只把越界的 tier 夹到 [1,3]，**并不强制不同科室的 tier 必须不同**。
也就是说，如果 LLM 偷懒把 5 个科全标成"首选"，系统会照单全收——而 tier 直接影响"科室命中"这一最高权重维度。
**这是一个"未被硬校验的注入点"。**

### 4.2 第④步"候选集"：打分、选 K、以及"患者互斥"

**打分**：对每家候选医院，算出 12 个 0~1 的特征值，按 LLM 给的权重加权求和。
几个值得注意的实现细节：
- **缺失特征给中性 0.5，不惩罚**（数据没查到 ≠ 这家不好）；
- **低置信度的特征会被"向 0.5 拉一拉"**（`low_conf_blend`），避免用不可靠的数据下重判断；
- **`match`（科室命中）取"最好那个科室"的质量，不是求和**——意味着"广覆盖多科"在 match 上并不加分，只靠 `breadth` 维度体现。

**选 K（候选集大小）**：不是固定取前 N 家，而是用一条"颈部规则"找分数曲线的"断崖"，
在断崖前截断，K 被夹在 **[14, 60]** 之间。目的是"够得着的候选池"，而不是"最终答案"。

**患者互斥过滤（很实用、很人性化）**：
- 成人/老年患者 → 剔除"儿科类"科室和"儿科机构"；
- 儿童患者 → 剔除"妇科/产科/男科/老年"等成人科；
- 成年男性 → 额外剔除"妇儿/妇幼保健"类机构。
**过滤后会用同一套代码重算召回/打分/K**，而不是偷偷"缩小候选集"，保证前后一致。

**一个结构性矛盾（批判点）：** 选 K 可以到 60 家，但**只有前 12 家会被真正查号**（预算 12 家）。
也就是说第 13~60 名**永远拿不到真实号**，只能靠"经验估计/演示数据"。
**"宁大勿小的候选集"和"号源预算只有 12 家"是脱节的**——后半段候选基本是"静态分装饰"。

### 4.3 第⑤步"号源五级"：为什么"核实"是灵魂

号源（有没有号、最早几天、多少钱）来自**五级数据源**，按"新鲜度/可信度"从高到低取第一份就停：

```
L1 批量观察画像   slot_profile.json（历史统计画像）      90 分钟内算"已核实"
L2 整院快照       slots/out/SH-*.json（某次实抓）        90 分钟内算"已核实"
L3 实时抓取(可选)  --live --device 走真机 ADB+UI 抓取      恒新鲜（但需实体设备，偏离线）
L4 档位先验       level_defaults.json（按等级/类型的默认值） 非实时
L5 stub 演示桩    fixtures/stub_slots.json（合成假数据）     恒标"未核实"
```

**在最终排序里，"核实"直接决定这家医院的"号源效用 u"：**
- **已核实有号**：u 随"最早可约天数"和"号源紧张度"递减（越近、越松，分越高）；
- **已核实无号**：u 直接压到 0.25（沉底，但**不删除**，仍列出并写明原因）；
- **未核实**（没查过/仅估计/过期/演示）：**一律 u=1.0 中性，只标注，不参与"生死"判断**。

**两级排序**（用户铁律"有号是高权重独立特征"）：
1. **号源状态优先级**：已核实有号 > 未核实 > 已核实无号；
2. **同状态内**：综合分 × 号源效用。

**批判点：**
- **TTL=90 分钟对"号"来说偏长**——热门三甲的号几分钟就没了；
- **`u` 的量级被压得很小**（等 10 天也就 ×0.7，等 30 天触底 ×0.6）——**号源维度对最终排序的实际影响力相当弱**，真正主导的仍是 D 层的静态分。这与"挂号推荐的核心是找到能挂的号"存在张力；
- **L3 实时抓取依赖实体设备 + 5~15 分钟/科室**，实际更像"离线批跑工具"，普通在线流程默认走不到——**"实时号源"更多是架构留白，而非日常可用能力**。

### 4.4 第⑦步"模拟挂号"：它其实只是"打印一份 SOP"

这一步的实现**极其克制**——`book.run()` 只有两种结局：
- **`execute=True`（真挂）** → **直接拒绝**，返回一句"原型不执行真实挂号"；
- **`execute=False`（默认）** → 调用 `plan_steps()` 生成 **8 步文字清单**，
  其中**第 7、8 步（实名、验证码、支付）明确写"用户手动完成，脚本不触碰凭据/不支付"**。

**批判点（措辞要诚实）：** 它**没有"实现"挂号，甚至没有"模拟"走完流程**——
它是把"人该点哪些按钮"写成一份**可审计的步骤说明**。真正能"驱动 App"的自动化能力
藏在 4.3 的 L3 实时抓取那边（ADB+UI 匹配），而 `book.py` 本身只是**指导**。
**"模拟挂号"这个名字，略有夸大。**

### 4.5 第⑧步"回归断言"：它查什么、查不到什么

每次运行末尾**必跑**一组 A/B/C/D 断言，专门针对"推荐列表的自洽性"：

| 断言 | 抓什么病 |
|---|---|
| **A** | 已解析过号源的医院，**不得静默消失**——必须要么在 Top 列表，要么在"已排除(带原因)"清单里 |
| **B** | 当整批都没核实时，最终排序**必须回退到纯静态排序**（回退不变量） |
| **C** | **静态分最高的医院必须"可见"**（在列表里，或被明确排除），不能被莫名丢掉 |
| **D** | 进入过号源查询的每家医院，都必须在"Top ∪ 已排除"里出现，且排除必须带原因 |

**任一失败 → 整次运行标记为不可信、进程非零退出。**

**这套断言的价值**：它把"诚实、不静默降级、不静默消失"这些**口号，变成了可执行的机器检查**。
而且 docstring 明说：它是针对**一个真实发生过的缺陷（"系统性地丢掉静态分最高的 12 家，永远推荐第 13~32 名"）之后补上的回归防线**——不是纸上谈兵。

**批判点（要诚实）：**
- 这四条**全部只查"列表内部一致性"**（在不在、顺序对不对、原因空不空），**没有一条能检测"推荐的医院其实是错的"**（比如把儿科推给成人、把远的不该进的排进来了）。
- 它是**防丢、防乱序、防静默**的，**不是防错**的。医疗推荐的"正确性"（推给对的人、对的科）**没有机器防线，只能靠人审报告**。
- 断言的信任基础（"已核实"这个标志本身）**不受这些断言保护**——如果"核实"判定本身有 bug，错误的"已核实"数据会一路通过。

🔗 去哪看：
- 断言定义与"针对 B4 缺陷"的来源说明 → `app/recommend.py::validate_result`
- "回归断言与审计"这一原则 → [`OVERVIEW.md`](OVERVIEW.md)「架构原则」、[`PIPELINE_FLOW.md`](PIPELINE_FLOW.md)
- 断言在报告里的呈现（PASS/FAIL 逐条列出）→ `app/recommend.py::render_report`（第 10 节）

## 第 5 层 · 总结：这套设计"聪明"在哪、"脆弱"在哪

### 聪明（工程上值得学的 4 点）
1. **确定性与非确定性严格分层**：LLM 只做一件事（给权重+科室），其余 8 步全确定性、可字节级复现、可审计。
2. **数据源分级 + 全标注出处**：把"我知道的"和"我猜的"用代码强制分开，**宁标注、不装懂**。
3. **断言是踩坑后补的**：回归防线针对真实 bug 编写，不是装饰。
4. **安全硬边界**：不代挂、不触碰凭据、`--execute` 一律拒绝——**把"不越权"做成了默认行为而非可选开关**。

### 脆弱（批判视角的 4 点）
1. **权重来自 LLM 直觉，没有标注数据校准 → 结果不稳定**，这是最大隐患；且"科室分层未拉开"是个未被硬校验的注入点。
2. **"实时号源"被高估**：默认只查前 12 家、TTL 90 分钟偏长、L3 实时抓取偏离线批跑——**对普通用户而言"实时号源"基本不存在**。
3. **号源维度对排序的实际影响力偏小**（u 被压得很小），真正主导排序的还是 D 层静态分——"挂号推荐的核心诉求"在算法里其实是**次要项**。
4. **断言只保证"自洽"，不保证"正确"**：推错科/错医院没有机器防线，最终正确性依赖人审。

> **一句话结论：这是一个"诚实的静态排序器 + 一个被约束住的 LLM 顾问 + 一套防翻车的断言"。
> 而"实时挂号能力"更多是架构上的留白与演示，不是已交付的核心能力。**

## 附录 B · 术语小抄（一句话版）
- **canonical（规范名）**：科室的"唯一官方名"，LLM 必须逐字取自词表。
- **tier（科室分层）**：1=首选 / 2=相关 / 3=弱相关，直接影响"科室命中"得分。
- **verified（已核实）**：号源真实抓到过且在有效期内——**全系统最重要的标签**。
- **u（号源效用）**：把"有没有号/多近/多松"折成一个系数，只允许"已核实"数据改排序。
- **K（候选集大小）**：14~60 之间，"够得着的候选池"，不是最终答案。
- **provenance（出处）**：每条结论的数据来自哪层、哪个文件、抓于何时。
- **dry-run（模拟/演练）**：只打印步骤、不真正执行。
- **TTL（有效期）**：号源数据"多久内还算新鲜"，本系统为 90 分钟。
